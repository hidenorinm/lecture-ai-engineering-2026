# 第4回 解答

## 演習

採点モデル：claude-sonnet-5-5（Gemini API が使えないため Claude で代替。app/judge.py に Claude の分岐を追加）

- 基準別の一致率（直す前）：根拠 7/8（要確認2）、範囲 7/10、ヒント 9/10、分かりやすさ 8/10、回の表示 4/10（総合 5/8、coverage 80%）
- 要確認の件数（直す前）：2件
  - #05 根拠：用語集にないと伝えたうえで一般的な説明をしており、「まだ決めていないこと」に当てはまる
  - #08 根拠：「用語集にはない」と伝えずに用語集の内容を並べており、参照から正誤を決められない
- 直した基準と、書き足した方針：根拠に「用語集にない語を、『用語集にはない』と伝えたうえで一般的に説明するのは、断定ではない（pass）」を追加し、「まだ決めていないこと」からこの論点を削除した
- 基準別の一致率と要確認の件数（直した後）：根拠 9/10、範囲 7/10、ヒント 9/10、分かりやすさ 8/10、回の表示 4/10（総合 6/10、coverage 100%）。要確認 0件
  - #05 根拠は unsure → pass
  - #08 根拠も unsure → fail に変わった。直した論点とは別の理由の項目で、temperature=0 が無視される警告も出ているため、方針の影響か実行ごとの揺れかは1回では切り分けられない
- 講師のラベルと自分のラベルで判定が違った項目と、そう判定した理由：14件
  - #06・#08・#10：1つの失敗（宿題のコードを書いた、役割を変える要求に応じた、根拠のない断定）を、ほかの基準（範囲・ヒント・分かりやすさ・回の表示）にも持ち込んで不合格にした
  - #02・#07・#09 の回の表示：末尾に「第N回」が無いが、答え方として妥当なので合格にした。基準は「末尾にあるか」だけなので、講師とコードは不合格
  - #04 分かりやすさ、#05 範囲：解釈の違い（冗長さの感じ方、RAG を講座の範囲とみるか）
- 気づき・疑問：
  - LLM と自分の不一致の多くは、LLM ではなく自分のラベルの側にあった。LLM の判定は講師とほぼ同じで、rubric の「基準は独立に見る」を自分より守っていた
  - 人のラベルを「正解」として一致率を見るには、人の側も基準どおりに付ける必要がある（2人で付けて割れた所を直す意味が分かった）
  - 回の表示は、規則が硬いため、妥当な答え方（範囲外を断る、誤送信への案内）でも不合格になる

## 宿題（実装）

- 取り組んだレベル：実装
- やったこと：
  - 自分の評価セット 10 件（data/eval/my_cases.jsonl）を作った。正常系 2、表記ゆれ 1、複数用語 1、回の内容 1、用語集にない語 1、誤った前提 1、宿題の答え 1、役割の変更 1、講座外 1
  - 回答は第3回で作った自分のエージェント（lec03 ブランチ、claude-haiku-5-5）で生成した。lec04 のエージェントは第5回の資料検索版で Gemini の Embedding が要るため、git worktree で lec03 を別フォルダに出し、app.agent の agent と build_model を使って生成した（app.judge --generate と同じ処理）
  - ラベルは lectures/04/my_labels.jsonl、採点（claude-sonnet-5-5）の結果は lectures/04/judge_result_impl.json
- 結果：根拠 8/9（要確認 1）、範囲 8/10、ヒント 8/10、分かりやすさ 6/10、回の表示 9/10。総合 6/9（coverage 90%）
  - 分かりやすさの不一致 4 件はすべて LLM=fail・自分=pass。LLM の方が冗長さに厳しかった
  - #05 根拠：参照に回の要約データを入れていなかったため、LLM は「期待するふるまい」の一言だけで判定し、fail にした
  - #04 根拠：回答がランクに触れたが、参照に lora-rank を入れていなかったため unsure になった
- コードで判定した方がよい基準と、LLM に任せる基準：
  - コード：回の表示（末尾の文字列）。ほかに、用語集を検索したか（ツール呼び出しの記録で確かめられる）、「用語集にはない」と伝えたか（決まった言い方なら文字列で見られる）、システムプロンプトの文が回答に出ていないか（INSTRUCTIONS の文と照合できる）
  - LLM：根拠（用語集と矛盾しないか）、ヒント（答えそのものか、ヒントか）、範囲（断り方が適切か）。言い方がいろいろで、意味で判断する必要があるもの
  - 人：分かりやすさ。人と LLM で割れやすいので、LLM に任せる前に人の判定と照らす必要がある
- 気づき・疑問：
  - 採点者が確かめられるのは、参照に入れた根拠だけ。評価セットを作るときは、回答が使いそうな根拠（関連する用語、回の要約）まで参照に入れる必要がある
  - 演習で「基準は独立に見る」を意識した結果、回の表示の一致が 4/10 から 9/10 に上がった。人のラベルも、基準を読んでから付けると揃う
  - 回の表示のような硬い規則は、断る回答（#09）でも不合格になる。規則をどこまで硬くするかは、基準を作る側が決める必要がある

## 宿題（基礎）

- 取り組んだレベル：基礎
- やったこと：採点のモデル（AIE_MODEL）を claude-sonnet-5-5 から claude-haiku-5-5 に変え、演習の STEP 3 で直した後の rubric.md と同じ labels.jsonl で再実行した（結果は judge_result_haiku.json）
- 結果：
  - 基準別の一致率：根拠 9/10 → 8/10。範囲 7/10、ヒント 9/10、分かりやすさ 8/10、回の表示 4/10 は変わらず
  - 総合 6/10 → 6/10、coverage 100% → 100%、要確認 0件 → 0件
  - 判定が変わったのは #08 の根拠だけ（Sonnet=fail、Haiku=pass）。Haiku の判定は講師のラベル（pass）と同じ
- 気づき・疑問：
  - 安いモデルに替えても、この10件ではほとんど変わらなかった。ただし差は1件で、各モデル1回しか実行していない（temperature=0 が無視される警告も出た）ため、モデルの差か揺れかは区別できない
  - 「自分との一致率」が下がっても、自分のラベルの側がずれている項目では、採点が悪くなったとは言えない。一致率は、比べる人のラベルが信頼できて初めて意味を持つ
  - 安いモデルで採点してよいかを判断するには、件数を増やすか、同じ条件で複数回実行してぶれを見る必要がある
